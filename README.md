# agentscaffold —— 给 AI 助手装「经验包」

AI 助手干活靠不靠谱，很大程度看它知不知道「这种时候该怎么做」。
这个项目就是把这种「做法」装进你的电脑或项目里：装好以后，遇到相应的事，它会自己照着做，
不用你每次重新交代一遍。

现在有一个经验包：**性能变慢了怎么办**。

## 性能变慢了怎么办

**什么时候用得上**

- 有人告诉你「某个测试从某天起慢了 12%」
- 你自己怀疑「我这次改的东西是不是把速度弄慢了」
- 你手里有改动前后两次跑的对比结果，不确定算不算真的变慢

**装上以后它会怎么做**

1. 先把事情查清楚：慢了多少、哪个测试、从哪天开始、当时改了哪些代码。
2. 判断是真是假：把改动前后各跑一遍，看能不能复现。复现不出来，它会直接说「大概率是噪声」，不硬往下猜。
3. 真慢了才去找原因：一般是对比两次跑的性能记录，看时间都花到哪儿去了。
4. 改一次、只跑最相关的那点测试、看数字，来回几轮——不是每轮都跑全套。
5. 收尾必须给结论：修好了 / 回退了 / 其实是噪声 / 这个变慢可以接受。不管哪种，都要带上数字。

**跟没有它相比**

| 没有它 | 有它 |
| --- | --- |
| 你问「为什么慢了」，它可能直接开始翻代码、改代码 | 它先说「我先跑一遍看看能不能复现」 |
| 一轮一轮地跑，来回等 | 一次就把「改前」和「改后」都跑了 |
| 它说「应该修好了」 | 它必须给出数字和明确结论 |
| 它可能顺手 push、顺手改别的文件 | 推送、回退、改 CI 之前都要先问你 |

**你要准备什么**

告诉它三件事：告警从哪来、改动前后怎么对比、性能记录用什么工具看。
写在一个小文件里（`.agents/perf-triage.config.json`），技能自带的说明书里有模板。
不写也行，它会先问你，而不是自己猜。

**它不管什么**

只管性能变慢这一类问题。单纯跑性能测试、分析你已经拿到手的性能记录、
测试失败 / 程序崩溃 / 编译不过，这些都不归它管。

<sub>这个经验包在文件和命令里的名字是 `perf-regression-triage`。</sub>

## 还有一个附加包（默认不装）

**「读懂一份性能记录」** —— 你手里已经有一份火焰图 / 采样结果 / CPU profile，
想知道时间到底花哪儿了。它负责：

- 先判断这份记录能不能信（时长够不够、样本够不够、符号有没有、是不是同一次实验）；
- 按大类归类（自己算 / 等锁 / GC / IO / 序列化 / 在等外部），先定方向；
- 定位到函数与调用栈，分清「它自己花的」和「它调用的」；
- 对号入座常见模式（锁竞争、分配抖动、正则回溯、反复解析、缺符号假热点……）；
- 最后给出能执行的结论：时间花在哪、候选改动按预期收益排序、哪些是证据哪些是猜测。

要装就加一句 `--add-packs profile-analysis`，或者交互式运行时在「是否安装附加技能包？」那一步勾它。

<sub>它在文件和命令里的名字是 `profile-analysis`。</sub>

## 怎么装

一条命令：

    agentscaffold init

默认只装在你自己电脑上，不碰任何项目，也不往任何代码仓库里放东西。

想让整个团队一起用，就装进项目：

    agentscaffold init --scope project

装进项目时会多问一次（因为里面有别人写的文件，见后面「关于别人的东西」），你确认了才会写。
不想回答提问就加 `--yes`；但装进项目时必须同时加 `--accept-mpl-notice`，表示你看过那份说明。

交互式运行时它会依次问你四件事：装到哪一层、装哪些技能包、要不要装**附加包**（默认一个都不装）、
要不要同时给 Claude Code 装一份。最后还会问一句要不要顺手把缺的工具装上。

## 装完之后，文件都在哪

| 装在哪 | 放了什么 |
| --- | --- |
| 只装自己（默认） | `~/.agents/skills/` 下多一个目录；另有一份 `~/.agents/AGENTS.md` |
| 装进项目 | 项目的 `.agents/skills/` 下多一个目录；项目根多一份 `AGENTS.md` |
| 上面再加 `--claude` | 再多给 Claude Code 一份，位置在 `~/.claude/` 或项目里的 `.claude/` |

`.agents/skills` 是这类助手通用的位置（Claude Code、Codex、DSH 等都读），所以默认放这儿就够了；
`--claude` 只是给 Claude Code 额外放一份。

`AGENTS.md` 是给助手看的一份「这个项目该怎么干活」的要求，里面留了空位让你填
（怎么构建、怎么跑测试等）。它只在第一次生成，之后再跑不会覆盖你自己填的内容。

装完它会顺手检查一遍技能要用到的外部工具，缺哪个、怎么装、缺了有什么退路都列出来。
这一步会问你要不要顺便把缺的装上——**默认一个都不装**，你勾了才装；
不想回答提问的模式下要装得显式加 `--install-tools`。

事后想再看一次这个检查：

    agentscaffold doctor

`doctor` 只检查、只给建议，不会装东西。

## 怎么卸掉

    agentscaffold uninstall

它会自己找装过的地方，列出来让你选（只装过一个也照样让你选），删掉的只是它当初装的那些文件。
你自己改过的文件不动，会列出来告诉你；真想连改过的一起删，加 `--force`。
只想看看它准备删什么、不真删，加 `--dry-run`。
没装过就直接报错，不会乱删东西。

## 它会不会帮我提交 git

会先问你。在项目里装完或卸完，它会问一句「是否把这次改动提交到当前仓库？」：

- 默认不提交；
- 只提交它这次动过的文件，你已经暂存的其它东西不受影响；
- 绝不 push；
- 如果这个目录还不是 git 仓库，它会问你要不要顺便建一个（默认不建）。

## 关于别人的东西

「性能变慢」这个经验包里的做法，是照着 Mozilla Firefox 项目公开的一份同类文件改的。
其中几份文件是原封不动搬过来的，按他们那份许可（MPL-2.0）保留，放在技能的 `upstream/` 目录里；
许可原文、来源说明、商标说明都跟着技能目录一起装，不会只丢在项目根。

对使用者的影响只有一条：这几份文件保持原样、带上许可说明。你项目里其它代码不受影响，
也不会因此要求你开源。我们自己重写的那部分，文件开头写明了「改过」。
本项目和 Mozilla、Firefox 没有关系，不是他们官方项目。

## 许可证

**这个工具本身：MIT。** 随便用、随便改、随便再分发，保留版权与许可声明即可。

**随包的技能文件：里面有几份是 MPL-2.0**（就是上一节说的那几份从 Firefox 搬来的）。
MPL-2.0 是「只约束被它覆盖的那几个文件」的许可，所以：

- 不要求你开源自己的项目，也不会改变你项目的许可证；
- 原样再分发：保留版权与许可声明、给出源码获取方式即可；
- 改动这几个文件后再分发：需要公开你改过的那几个文件；
- **不要把这几份文件的内容合并进你自己的源文件**——合并后的文件可能整体受 MPL 约束；
- 不得用 Mozilla / Firefox 的名字或 logo 暗示官方背书。

**商标单独说：** MPL-2.0 只授权版权，不授权商标。Mozilla、Firefox 及 Firefox 徽标是
Mozilla Foundation 的商标。本项目与 Mozilla 无隶属或背书关系，只是「受 Firefox 工作流启发」。

**想看完整清单：** 跑 `agentscaffold --license` 会列出每一个受 MPL 约束的文件、来源仓库与固定提交；
要给合规工具或 agent 读，用 `agentscaffold --license --json`。
逐文件说明也会随技能一起装到技能目录里（`THIRD-PARTY-NOTICES.md`），不只在项目根。

## 想再给它加一个经验包

在 `packs/` 下新建一个目录，放一个 `pack.json`（写明包名、说明、包含哪些技能、依赖哪些工具），
技能本体是 `skills/<名字>/SKILL.md`——一份说明书，开头两行要写清「什么时候该用它、什么时候不该用」。
字段含义和写作要点见 [DETAILS.md](DETAILS.md)。
