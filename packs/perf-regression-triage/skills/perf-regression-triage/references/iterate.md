# 迭代到修复

循环只有三步：**改一处 → 跑最小对照 → 看数字**。这个文件的存在意义是让每一轮都便宜。

## 每一轮

1. **一次只改一处**，并且明确写出这一处的假设（例如"这次分配可以省掉"）。
   同时改三处，即使数字变好了，你也不知道是哪一处起的作用。
2. **收窄对照**：只跑回归最严重的那一个测试/基准，只留一个平台，
   重复次数取到能区分信号与噪声的最小值。
3. **记录**：改动、命令、base 数字、new 数字、是否超出噪声。把这张表留着，
   最后写结论时直接用它。

## 什么时候才跑完整的一批

只有**最后一次确认**才跑完整的告警测试集与全部平台。中途跑完整集是把钱花在不需要的地方。

## 常见坑

- **把基准改绿**：调整输入规模、放宽阈值、改断言让数字好看，这不是修复。发现自己在做这件事，停下来说明情况。
- **只看百分比不看绝对值**：小基数的 30% 可能只是几十微秒，判断是否值得继续要先看绝对值与噪声。
- **跨机型比较**：不同 runner/机器上的数字不可直接比，对照必须在同类机器上。
- **重复次数不足**：两组分布重叠时不要下结论，加次数或者收窄到单测试。
- **忘记 base**：每轮都要有同一批条件下的 base 数字，否则你比的是"今天 vs 上周"。

## 什么时候停

- 数字回到噪声范围内 → 完成，进入 `close-out.md`。
- 找到的是"这个回归其实可以接受"（例如为了某个正确性收益付出的代价）→ 走 `close-out.md` 的接受路径，
  但必须把两边的数字与理由都记下来。
- 连续几轮都没有改善 → 回头重新确认第 2 步的复现结论，别在错误的假设上加码。
