# 关闭回归单

第 2 步确认结果、第 4 步的迭代记录，到这里都要落到明确结论上。**没有"大概修好了"这种关闭方式。**

## 四种结论

1. **修复**：改动已让数字回到噪声范围内。
   记录：改动、base/new 数字、重跑次数、平台、判定命令。
2. **回退（back out）**：收益小于代价，或短期无法修。
   记录：回退的 revision、回退后的数字、原改动会不会被重新提交。
3. **确认是噪声**：base 与 new 分布重叠，且多次重跑仍复现不出差异。
   记录：重跑次数与两组数字，明确写出"未复现"。
   注意：只是"这次没复现"不等于"这个告警是假的"，把观察到的次数写清楚。
4. **确认是可接受的取舍**：确实变慢了，但换来了明确的正收益（正确性、可维护性、别的场景的显著提升）。
   记录：变慢的幅度、换来的收益、谁认可这个取舍。**取舍得由人拍板，不能由 agent 自行认定。**

## 必须留下的信息

- 告警 ID 与 culprit revision（含 base/new 两个 revision）
- 复现结论：复现 / 未复现 / 模棱两可，以及支撑它的重跑次数
- 数字：base 与 new，绝对值与百分比，同机型同批测试
- 结论与理由；若为取舍，另有认可人
- 后续动作：谁跟进、什么条件下重开

## 报告写法

- 先说结论，再给支撑数字；不要把过程流水账当结论。
- 引用代码用名字不用行号（`函数名`、`类名`、`配置项`），需要定位时给固定 revision 的 permalink。
- 百分比与绝对值一起给；只有百分比时补上基数。

## 排期与提醒

- 如果项目规定了"引入回归的提交有 N 个工作日响应窗口"，**第 1 步就要确认这个窗口是否在走**，
  临近到期要主动提醒用户，不要等它过期。
- 任何回退、推送、改 CI 的动作都要用户明确批准后再做。

## 把反馈交回来

这条技能本身也需要维护。遇到下面情况，把具体现象记下来并反馈给维护者：

- 技能里写的步骤在你的项目里跑不通（适配器缺失或写错）
- 某个"坑"文档里没写，但实际踩到了（例如某过滤参数不生效）
- 某一步的成本明显高于必要（比如默认要跑完整测试集）

反馈时给**可复现的具体信息**（命令、输出、环境），不要只说"不好用"。
