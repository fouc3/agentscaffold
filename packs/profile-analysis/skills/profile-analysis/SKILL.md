# 性能记录怎么看

## 三条铁律

1. **不读原始 profile**：动辄几万行 JSON，读进来只会烧上下文。一律让工具去查，只把结论带回来。
2. **先粗后细**：先看「时间大致花在哪一大类」，再看具体函数。一上来盯着某个函数会迷路。
3. **分清自身耗时与被调用耗时**：`self` 是这个函数自己花的，`total` 包含它调用的东西。
   拿 `total` 当 `self` 用，追到的往往是调用方而不是问题所在。

## 第 1 步：这份记录能不能用

先花一分钟判断可信度，不可信就别往下分析：

- **时长**：不到 1 秒的记录基本是噪声，看大局也要几秒以上。
- **样本量**：只有几百个样本时，占比差几个百分点没有意义。
- **符号**：如果热点里大量是地址或 `[unknown]`，先解决符号（带 debug 信息重跑），
  否则你只能看到「某个未知地址很慢」。
- **一致性**：是不是同一输入、同一台机器、同样的负载条件跑出来的。跨机型比较没有意义。

## 第 2 步：时间花在哪一大类

按下面几类先归一次类，通常一眼就能看出方向：

| 大类 | 特征 | 往下看什么 |
| --- | --- | --- |
| 自己算 | 热点集中在少数几个纯计算函数 | 算法与数据结构、循环里的重复工作 |
| 等锁 / 等别的线程 | 大量时间在 `pthread_mutex_lock`、`futex`、`__psynch` 一类符号上 | 锁粒度、临界区里做了什么、是否有共享写 |
| 垃圾回收 / 内存管理 | GC 线程或 `malloc/free`、`operator new` 占大头 | 分配次数与对象生命周期 |
| IO / 系统调用 | `read`/`write`/`recv`/`open` 等 | 批量大小、次数、是否同步等待 |
| 序列化 / 解析 | JSON、protobuf、正则、模板引擎函数 | 能否跳过、能否复用结果 |
| 空闲 / 等待外部 | 主线程长时间 `poll`/`epoll_wait`、帧间空转 | 不是 CPU 问题，别优化 CPU |

## 第 3 步：定位到函数与调用栈

- 从占比最高的分支**一次只往下钻一层**，每层都问「这里的时间是它自己花的，还是它调用的？」。
- **看调用栈**：同一个函数可能从两条完全不同的路径进来，值得修的是其中一条。
  用 `self` 排序找热点函数，再用调用栈确认它是被谁调进来的。
- 递归与内联会让 `total` 虚高：递归函数的 `total` 会把所有层加起来，别直接当占比。

## 第 4 步：对号入座

拿到热点后，用 [references/patterns.md](references/patterns.md) 里的模式逐条对：
自旋／锁竞争、分配抖动、反复解析同一份数据、字符串拼接、拷贝、正则回溯、
缺符号导致的假热点。每条都写了「看到什么现象 → 大概率是什么 → 先验证什么」。

## 第 5 步：把结论写成人能执行的东西

- 一句结论：**时间主要花在哪**（附支撑数字：样本数、占比、绝对时间）。
- 候选改动按**预期收益**排序，每条写清「收益从哪来」（少一次分配？少一次锁竞争？少一趟 IO？）。
- 明确区分**证据**与**猜测**：哪一条是记录里直接看到的，哪一条是你的推断。
- 不要给「可以优化一下」「建议深入分析」这类结论——等于没说。
