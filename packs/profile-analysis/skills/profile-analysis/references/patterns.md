# 常见热点模式：看到什么 → 大概率是什么 → 先验证什么

按「现象」查表。每条都给了验证方法，**验证优先于动手改**：先证明它，再改。

## 1. 锁竞争 / 自旋

- **现象**：`futex`、`pthread_mutex_lock`、`__psynch_mutexwait`、`park`、`Monitor.Enter` 占大头；
  多线程版本比单线程还慢。
- **大概率**：临界区太大，或者多个线程抢同一把锁。
- **先验证**：把临界区缩小或换成无锁结构跑一次，看锁等待是否消失、总时间是否下降；
  单线程跑同一负载作为下限参考。

## 2. 分配抖动 / GC 频繁

- **现象**：GC 线程或 `malloc`/`free`/`operator new`/`_int_malloc` 占比高；耗时抖动大。
- **大概率**：循环里反复创建临时对象、容器每次扩容、字符串拼接。
- **先验证**：统计分配次数（很多语言有内置埋点），把「每次循环都分配」改成「循环外分配一次」
  再看占比；若 GC 占比下降而总时间不变，说明瓶颈在别处。

## 3. 反复解析同一份数据

- **现象**：JSON／YAML／protobuf／模板引擎／正则相关函数在多条栈里反复出现。
- **大概率**：同一份输入被解析多次，或解析结果没缓存。
- **先验证**：在解析函数上打个计数器（或看调用次数），确认调用次数是否远超实际需要。

## 4. 字符串与拷贝

- **现象**：`memcpy`、`strlen`、`strcat`、`StringBuilder`、`substring`、`concat` 占比高。
- **大概率**：循环里做字符串拼接、反复拷贝大块数据、返回副本而不是引用。
- **先验证**：把拼接改成一次性构造、把拷贝改成视图/切片，观察拷贝类符号是否退出热点。

## 5. 正则回溯

- **现象**：正则引擎函数（`backtrack`、`match`、`exec`）占比高且耗时不稳定。
- **大概率**：表达式有嵌套量词，遇到长输入时指数级回溯。
- **先验证**：用短输入与长输入各跑一次——如果耗时不是线性增长，基本就是回溯。

## 6. 同步 IO 串行化

- **现象**：`read`/`write`/`recv`/`fsync`/`open` 链路在关键路径上，且时间随数据量线性增长。
- **大概率**：一次一条地取数据、每次读写都很小、没有批量或并行。
- **先验证**：合并成批量调用或加并发，看总时间是否成比例下降。

## 7. 像素级热点（真·计算）

- **现象**：热点集中在少数纯计算函数上，`self` 占比高，没有系统调用与锁。
- **大概率**：算法问题（复杂度高、重复计算）；也可能是编译没开优化。
- **先验证**：确认构建类型（release/opt）与优化开关；再用不同规模输入看耗时曲线，
  判断是常数因子问题还是复杂度问题。

## 8. 空闲 / 等待外部

- **现象**：主线程大量 `epoll_wait`/`poll`/`select`/`(idle)`，CPU 占用不高但端到端很慢。
- **大概率**：不是 CPU 问题——在等网络、数据库、磁盘或下游服务。
- **先验证**：看端到端时间与 CPU 时间的差；查下游的响应时间分布，而不是继续优化 CPU 代码。

## 9. 缺符号造成的假热点

- **现象**：一大块 `[unknown]` / 地址 / `__memmove_avx_unaligned` 之类出现在热点顶部。
- **大概率**：没带符号，或者被优化/内联掉了；`memmove` 这类通常是现象不是原因（谁在 memmove？）。
- **先验证**：带 debug 信息重跑一次；对 `memmove`/`memset` 这类，往调用栈上一层看是谁在调。

## 10. 单点热点 vs 长尾

- **单点**：一个函数占 40% 以上 → 直接看它。
- **长尾**：几十个函数各占 1–3% → 不要逐个优化；先找它们的共同调用方
  （通常是某个循环或某次请求处理），从结构上解决。
